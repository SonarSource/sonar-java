This rule raises an issue when a method annotated with TestNG’s @DataProvider returns a type that is not one of the supported return types: Object[][], Iterator<Object[]>, or Object[].

Why is this an issue?

TestNG relies on the @DataProvider annotation to supply test data for parameterized tests. For TestNG to properly execute these tests, @DataProvider methods must return one of the specifically supported types:

  • Object[][] - a two-dimensional array where each inner array represents parameters for one test invocation
  • Iterator<Object[]> - an iterator of arrays for lazy evaluation of test data
  • Object[] - an array where each element is itself an Object[] (available since TestNG 6.x)

When a @DataProvider method returns an incompatible type (such as List, Stream, or a simple array), TestNG cannot process the data correctly. This causes test failures at runtime, even though the code may compile successfully.

Using the wrong return type breaks the contract between your test code and the TestNG framework, leading to:

  • Tests that fail to execute
  • Misleading error messages
  • Wasted debugging time
  • Reduced confidence in your test suite

What is the potential impact?

When a @DataProvider method returns an invalid type, the immediate impact is test execution failure. TestNG will throw a runtime exception when attempting to invoke the test method with the provided data.

This has several consequences:

  • Delayed feedback: The error only appears at runtime, not during compilation, making it harder to catch during development
  • Broken test suites: Entire test classes may fail to run if the data provider is misconfigured
  • False negatives: You might believe your code is untested when tests simply aren’t executing
  • Maintenance burden: Team members unfamiliar with TestNG’s requirements may struggle to understand and fix the issue

In CI/CD pipelines, this can block deployments and require emergency fixes to restore test coverage.

How to fix it in TestNG

Use Object[][] when you have a fixed set of test data. Each inner array represents the parameters for one test invocation.

Code examples

Noncompliant code example

@DataProvider
public List<String> provideData() {  // Noncompliant
    return Arrays.asList("value1", "value2", "value3");
}

Compliant solution

@DataProvider
public Object[][] provideData() {
    return new Object[][] {
        {"value1"},
        {"value2"},
        {"value3"}
    };
}

Use Iterator<Object[]> when you need lazy evaluation or want to generate test data on-the-fly. This is useful for large datasets or when data generation is expensive.

Noncompliant code example

@DataProvider
public Stream<String> provideData() {  // Noncompliant
    return Stream.of("value1", "value2", "value3");
}

Compliant solution

@DataProvider
public Iterator<Object[]> provideData() {
    return Arrays.asList(
        new Object[]{"value1"},
        new Object[]{"value2"},
        new Object[]{"value3"}
    ).iterator();
}

Use Object[] where each element is itself an Object[] (available since TestNG 6.x). This can be useful when building data sets dynamically.

Noncompliant code example

@DataProvider
public String[] provideData() {  // Noncompliant
    return new String[]{"value1", "value2", "value3"};
}

Compliant solution

@DataProvider
public Object[] provideData() {
    return new Object[]{
        new Object[]{"value1"},
        new Object[]{"value2"},
        new Object[]{"value3"}
    };
}
