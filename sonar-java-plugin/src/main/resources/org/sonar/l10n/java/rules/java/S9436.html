When a class declares more than one logger, part of its log output is emitted under a category that nobody configured, so those messages are silently dropped or written to the wrong destination.

Why is this an issue?

A logger is created for a category, usually the name of the class that owns it. Logging configuration, such as a Logback or Log4j 2 configuration file, attaches levels and appenders to that category. A class is therefore expected to log through a single logger, so that its output is filtered and routed as one unit.

A second logger field breaks that. Its messages are governed by whatever the configuration says about the other category, in practice the root level, so they are filtered out below that threshold or appended to a file meant for another component. The level set for the class then controls only half of its output: raising it to DEBUG during an incident produces a partial trace, with no indication that anything is missing. The failure is silent, which is what makes it expensive, as it is usually discovered while investigating an incident with the logs that were supposed to explain it.

A second logger field is almost always accidental: a field copied from another class, a leftover from a refactoring that split or merged classes, or two logging facades mixed in the same file.

This rule raises an issue when a class declares more than one logger field, for SLF4J, Log4j, Log4j 2, Commons Logging and java.util.logging.

public class PaymentService {
  private static final Logger LOG = LoggerFactory.getLogger(PaymentService.class);
  private static final Logger AUDIT = LoggerFactory.getLogger(OrderService.class); // Noncompliant: audit messages are logged under the "OrderService" category
}

Exceptions

A nested or inner class is a class of its own, so a logger it declares is not counted against the logger of the enclosing class. Only the fields declared directly in the same class body are counted together.

A non-static logger field declared next to a static one still raises an issue, because both create a logging category and the problem described above applies regardless of the modifiers. Rule {rule:java:S1312} covers the modifiers a logger field should have.

How to fix it

Keep a single logger, named after the class, and remove the extra field. Redirect the calls made on the removed logger to the remaining one.

The second logger is sometimes deliberate: a separate stream is wanted for audit or metrics messages, so that they can be routed to their own file and kept at their own level. In that case, do not simply merge the calls, as that would lose the distinction. Tag the messages with an SLF4J Marker instead: create the marker once with MarkerFactory.getMarker("AUDIT"), pass it as the first argument of the logging call, and route it in the logging configuration with a marker filter. A marker keeps the routing configurable without introducing a category that does not match any class.

With Log4j 2, MarkerManager.getMarker plays the same role. With java.util.logging, which has no marker concept, keep the single logger and either use a dedicated level or a Filter on the handler.

Code examples

Noncompliant code example

public class PaymentService {

  private static final Logger LOG = LoggerFactory.getLogger(PaymentService.class);
  private static final Logger AUDIT = LoggerFactory.getLogger(OrderService.class); // Noncompliant

  public void capture(Payment payment) {
    LOG.debug("Capturing payment {}", payment.id());
    gateway.capture(payment);
    AUDIT.info("Payment {} captured for {}", payment.id(), payment.amount());
  }
}

Compliant solution

public class PaymentService {

  private static final Logger LOG = LoggerFactory.getLogger(PaymentService.class);
  private static final Marker AUDIT = MarkerFactory.getMarker("AUDIT");

  public void capture(Payment payment) {
    LOG.debug("Capturing payment {}", payment.id());
    gateway.capture(payment);
    LOG.info(AUDIT, "Payment {} captured for {}", payment.id(), payment.amount());
  }
}

How does this work?

The audit messages are now emitted under the PaymentService category, so the level configured for the class governs all of its output. The AUDIT marker carries the distinction that the second logger used to carry, and a marker filter in the logging configuration can still send those messages to a dedicated appender.

The refactoring preserves behavior as long as every call moved to the remaining logger keeps its level and its arguments, and the configuration that targeted the removed category is replaced by a marker filter. Check the logging configuration before deleting a logger field, otherwise messages that used to be written to a dedicated file silently move to the main log.
