This rule raises an issue on a private, non-final instance field whose value is assigned only during object initialization and never reassigned afterwards. Such a field is already immutable in practice, and declaring it final states that contract in the code instead of leaving it to be rediscovered.

Why is this an issue?

A private instance field whose only assignments happen during object initialization, in its declaration, in an instance initializer block, or in a constructor, never changes value once the constructor returns. As long as it is not declared final, nothing says so:

  • A reader who needs to know whether the value can change has to scan the whole class for another assignment.
  • A later change can reassign the field by mistake, and the compiler will accept it. With final, the same mistake does not compile.
  • The field has no safe-publication guarantee. A final field is guaranteed to be visible, fully initialized, to any thread that reads the object after construction, even if the reference was published without synchronization.

Note that final is shallow: it freezes the reference, not the object behind it. A final List field can still have elements added to it, and a final field holding a mutable object says nothing about that object’s state. Use final to express "this field always points at the same value", not "this object cannot change".

Exceptions

No issue is raised in the following cases.

  • Fields that are not private. Proving that a package-private, protected or public field is never reassigned would require analyzing every class that can see it, so the rule deliberately stops at private.
  • Fields assigned by a framework through reflection, outside any constructor. Adding final to those fields breaks the framework or the build. This covers at least:
    • JPA and Hibernate entity fields, for example fields in a type annotated with @Entity or @Embeddable, and fields annotated with @Id, @Column, @ManyToOne or @OneToMany.
    • Deserialization targets, for example fields annotated with @JsonProperty, @JsonCreator, @XmlElement or @JsonbProperty.
    • Injected fields, for example fields annotated with @Autowired, @Value, @Inject, @Resource or @PersistenceContext.
    • Lombok-generated code, for example fields in a type annotated with @Setter, @Data or @Builder.
    • Test doubles, for example fields annotated with @Mock, @Spy, @InjectMocks or @Captor.
  • Fields that are not assigned exactly once by a statement placed directly in the body of every constructor that does not delegate to another one with this(…​). This covers fields assigned inside a conditional, a loop or a try block, and fields assigned in a constructor that can return early. A final field must be definitely assigned by the end of each constructor, and the rule does not follow the control flow to prove it in these cases.
  • Lazily initialized fields, assigned on first use rather than during construction, including caches and memoized values.
  • Fields reassigned through a reference to the object under construction that escapes the constructor, for example a field written by a callback invoked from the constructor.

How to fix it

Add the final modifier to the field declaration. The change preserves behavior: if the code compiles afterwards, the field was effectively final already, and final only documents it and locks it in.

If the compiler then rejects the field because it is "possibly already assigned" or "might not have been initialized", the field is not effectively final after all, and the issue should be reviewed instead of fixed. That happens when an assignment was missed on a constructor path or when the field is assigned more than once.

An issue on a field that a framework writes by reflection through an annotation this rule does not know about is a false positive and should be reported as such. An issue on a field that is effectively final today but is expected to become mutable as the class evolves is a genuine match, and leaving it as-is is a deliberate trade-off rather than a false positive.

Do not reach for final as a way to make a class immutable. A field pointing at a mutable object stays mutable through that object, so also consider defensive copying or an unmodifiable view if immutability is the goal.

Code examples

Noncompliant code example

public class ShipmentTracker {

  private String carrier; // Noncompliant: assigned only in the constructor
  private int deliveredCount;
  private final List<String> events = new ArrayList<>();

  public ShipmentTracker(String carrier) {
    this.carrier = carrier;
  }

  public void recordDelivery(String trackingNumber) {
    deliveredCount++;
    events.add(carrier + ":" + trackingNumber);
  }
}

The deliveredCount field is incremented in recordDelivery, so it is genuinely mutable and no issue is raised on it.

Compliant solution

public class ShipmentTracker {

  private final String carrier;
  private int deliveredCount;
  private final List<String> events = new ArrayList<>();

  public ShipmentTracker(String carrier) {
    this.carrier = carrier;
  }

  public void recordDelivery(String trackingNumber) {
    deliveredCount++;
    events.add(carrier + ":" + trackingNumber);
  }
}
