An issue is raised when string formatting functions that substitute placeholders with values are used as arguments to methods that already support formatting or parameterized messages natively.

In Java, this specifically refers to String.format.

Why is this an issue?

Many APIs provide built-in formatting capabilities. When you wrap generic string formatting functions around these APIs, you’re adding an unnecessary layer that hurts both performance and readability.

Performance concerns

Generic string formatting functions are typically eagerly evaluated. This means the formatted string is created immediately, even if it’s never used. This is particularly problematic in logging scenarios:

LOG.debug(format("Processing %d items", items.size())); // Always formats, even if DEBUG is disabled

When the debug level is disabled, the application still pays the cost of:

  • Creating the format string
  • Boxing primitive values into objects
  • Parsing the format specifiers
  • Building the final string

Logging frameworks provide parameterized logging that defers string construction until the message is actually needed:

LOG.debug("Processing {} items", items.size()); // Only formats if DEBUG is enabled

Readability and idioms

Each API has its own idiomatic way of formatting. Using generic string formatting makes the code less recognizable to developers familiar with these frameworks:

  • Logging frameworks use their own placeholder syntax
  • Output stream APIs have their own formatting methods
  • String builder APIs are designed for efficient concatenation

Using the native approach makes your intent clearer and your code more maintainable.

When generic formatting defeats the purpose

Some APIs are specifically designed for performance. Using generic string formatting with them undermines their benefits:

StringBuilder sb = new StringBuilder();
sb.append(format("User: %s, Age: %d", name, age)); // Creates intermediate String object

The string builder API is meant to avoid creating intermediate string objects, but generic formatting functions create one anyway, negating the performance benefit.

In Java, this specifically refers to String.format(). Common APIs with their own formatting include SLF4J (using {} placeholders), PrintStream and PrintWriter (with printf methods), and StringBuilder (designed for efficient string concatenation).

What is the potential impact?

Using redundant manual string formatting can lead to:

  • Performance degradation: In high-throughput applications, especially those with extensive logging, the unnecessary string formatting can waste significant CPU cycles and create memory pressure from temporary objects.
  • Maintainability issues: Code that doesn’t follow framework conventions is harder for other developers to understand and maintain, increasing the likelihood of bugs during refactoring.
  • Inconsistent codebase: Mixing manual string formatting with native API calls creates inconsistency, making the code harder to review and understand.

In Java, this specifically refers to redundant String.format calls.

How to fix it in SLF4J

SLF4J and similar logging frameworks (Log4j2, Logback) support parameterized logging with {} placeholders. This approach defers string construction until the log level is enabled.

Code examples

Noncompliant code example

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

class UserService {
  private static final Logger LOG = LoggerFactory.getLogger(UserService.class);

  void activateUser(String username, String role) {
    LOG.info(String.format("Activated user '%s' with role '%s'", username, role)); // Noncompliant
  }
}

Compliant solution

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

class UserService {
  private static final Logger LOG = LoggerFactory.getLogger(UserService.class);

  void activateUser(String username, String role) {
    LOG.info("Activated user '{}' with role '{}'", username, role);
  }
}

How to fix it in System.out/System.err

For console output, use printf instead of println with String.format. The printf method supports the same format specifiers as String.format.

Code examples

Noncompliant code example

class Calculator {
  void displayResult(int a, int b, int sum) {
    System.out.println(String.format("Result: %d + %d = %d", a, b, sum)); // Noncompliant
  }
}

Compliant solution

class Calculator {
  void displayResult(int a, int b, int sum) {
    System.out.printf("Result: %d + %d = %d%n", a, b, sum);
  }
}

How to fix it in PrintStream/PrintWriter

Both PrintStream and PrintWriter provide printf and format methods. Use these instead of wrapping String.format in print or println.

Code examples

Noncompliant code example

import java.io.PrintWriter;

class ReportGenerator {
  void writeHeader(PrintWriter writer, String title, int pageNum) {
    writer.println(String.format("Page %d: %s", pageNum, title)); // Noncompliant
  }
}

Compliant solution

import java.io.PrintWriter;

class ReportGenerator {
  void writeHeader(PrintWriter writer, String title, int pageNum) {
    writer.printf("Page %d: %s%n", pageNum, title);
  }
}

How to fix it in StringBuilder

StringBuilder is designed for efficient string concatenation. Using String.format with it creates an unnecessary intermediate String object, defeating the purpose. Use chained append calls instead.

Code examples

Noncompliant code example

class ReportBuilder {
  String buildUserSummary(String name, int age, String email) {
    StringBuilder sb = new StringBuilder();
    sb.append(String.format("User: %s, ", name)); // Noncompliant
    sb.append(String.format("age: %d, ", age)); // Noncompliant
    sb.append(String.format("email: %s", email)); // Noncompliant
    return sb.toString();
  }
}

Compliant solution

class ReportBuilder {
  String buildUserSummary(String name, int age, String email) {
    StringBuilder sb = new StringBuilder();
    sb.append("User: ").append(name).append(", ");
    sb.append("age: ").append(age).append(", ");
    sb.append("email: ").append(email);
    return sb.toString();
  }
}

How to fix it in Exception constructors

For simple exception messages, string concatenation is clearer and more efficient than String.format. The + operator is optimized by the Java compiler and doesn’t require parsing format specifiers.

Code examples

Noncompliant code example

class Validator {
  void validateAge(int age) {
    if (age < 0) {
      throw new IllegalArgumentException(String.format("Age cannot be negative: %d", age)); // Noncompliant
    }
  }
}

Compliant solution

class Validator {
  void validateAge(int age) {
    if (age < 0) {
      throw new IllegalArgumentException("Age cannot be negative: " + age);
    }
  }
}
