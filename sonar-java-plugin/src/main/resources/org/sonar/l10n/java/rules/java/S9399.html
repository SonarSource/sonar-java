This is an issue when instance-level member data is protected by a class-level lock or synchronized using a shared field that is common to all instances of the class.

Why is this an issue?

Locks in multi-threaded programming control access to shared data. When a lock protects a field, both the lock and the field must have the same scope.

A class-level lock (also called a static lock) is shared across all instances of a class. It should only guard class-level fields (static fields) that are shared across all instances.

An instance-level lock belongs to a specific object instance. It should guard instance fields that are specific to that object.

When you use a class-level lock to guard an instance field, the lock provides no real protection. Different object instances will compete for the same lock even though they’re accessing different data. This creates unnecessary contention and can cause performance problems.

In Java, class-level locks are implemented using static fields:

private static final Object LOCK = new Object();

This creates a lock that is shared across all instances of the class.

What is the potential impact?

This synchronization mismatch can cause race conditions leading to data corruption, incorrect calculations, or inconsistent object state. In multi-threaded applications, this can manifest as intermittent bugs that are difficult to reproduce and diagnose.

How to fix it

Use an instance-level lock to guard instance fields. This ensures each object instance has its own lock, properly protecting its own state.

Code examples

Noncompliant code example

class Counter {
    private static final Object LOCK = new Object();
    private int count = 0;

    public void increment() {
        synchronized(LOCK) {  // Noncompliant
            count++;
        }
    }
}

Compliant solution

class Counter {
    private final Object lock = new Object();
    private int count = 0;

    public void increment() {
        synchronized(lock) {
            count++;
        }
    }
}
