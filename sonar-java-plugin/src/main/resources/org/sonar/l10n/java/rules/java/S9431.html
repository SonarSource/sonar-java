This rule raises an issue when a class directly extends the root exception base class in the language’s exception hierarchy.

In Java, this specifically refers to the java.lang.Throwable class.

Why is this an issue?

In this language, all exceptions and errors inherit from a root exception class. However, directly extending this root class is considered poor practice because it creates ambiguity in your exception hierarchy.

The exception system is built around two distinct categories:

  • Compiler-enforced exceptions (extending the recoverable exception class): These represent recoverable conditions that calling code should handle. The compiler enforces that these exceptions are either caught or declared in the function signature.
  • Runtime exceptions (extending the unchecked exception class): These represent programming errors or unrecoverable conditions. The compiler does not require them to be caught or declared.

When you extend the root exception class directly, it is unclear whether your exception is compiler-enforced or unchecked. This creates confusion for developers using your exception class:

  • They don’t know if they need to handle it (compiler-enforced) or if it indicates a programming error (unchecked)
  • Exception handling code becomes less predictable
  • The intent of your exception class is obscured

The language’s API design guidelines and best practices consistently recommend extending either the recoverable exception class or the unchecked exception class to make your intent clear. This convention is followed throughout the standard library and third-party libraries.

Additionally, the system-level error class also extends the root exception class, but it is reserved for serious system-level problems (like out-of-memory conditions). Custom application exceptions should never extend the system-level error class.

In Java specifically, the root exception class is Throwable, the recoverable exception class is Exception, the unchecked exception class is RuntimeException, and the system-level error class is Error. For example, serious system-level problems include OutOfMemoryError.

What is the potential impact?

This issue primarily affects code maintainability and clarity:

  • Developers may be confused about whether to handle your error type using standard error handling mechanisms or declare it in function interfaces
  • Code reviews become more difficult because the error type’s purpose and relationship to the standard error hierarchy is ambiguous
  • Error handlers that catch standard error types may not catch your custom error class, leading to unexpected behavior
  • The codebase becomes harder to understand and maintain over time

How to fix it

If you want a checked exception (one that must be declared or caught), extend Exception instead of Throwable. Checked exceptions are appropriate for recoverable conditions that calling code should handle.

Code examples

Noncompliant code example

public class CustomException extends Throwable { // Noncompliant
    public CustomException(String message) {
        super(message);
    }
}

Compliant solution

public class CustomException extends Exception {
    public CustomException(String message) {
        super(message);
    }
}
