This is an issue when calling APIs that perform runtime lookups of methods or fields where the specified type signature does not match the actual target method or field type.

In Java, this specifically refers to MethodHandle and VarHandle lookup methods.

Why is this an issue?

Language runtimes provide mechanisms for dynamic method invocation and field access that operate through programmatically constructed handles or references. These mechanisms allow code to invoke methods and access fields with better performance than traditional string-based reflection approaches.

When creating these dynamic invocations, you must programmatically specify the exact type signature of the target method or field, including all parameter types and return types. If this constructed signature doesn’t match the actual target’s signature, the operation will fail at runtime with an exception.

The compiler cannot verify these type signatures because they are constructed dynamically at runtime rather than being statically declared in code. This means type mismatches that could be caught during development will only surface when the code executes, potentially in production.

Common mistakes include:

  • Using the wrong parameter types (e.g., string types instead of numeric types)
  • Using the wrong return type
  • Forgetting parameters or including extra ones
  • Using boxed/wrapper types instead of primitive types, or vice versa
  • Incorrect ordering of parameters

What is the potential impact?

When the type signature doesn’t match, the code will throw runtime errors in these scenarios:

  • When looking up a method with a signature that doesn’t exist
  • When looking up a field with the wrong type
  • When the dynamically obtained reference is invoked with incompatible types

These runtime failures can cause application crashes, service disruptions, or unexpected behavior in production environments. Since these are dynamic invocation errors that may bypass compile-time checking, they may not be caught by standard error handling and can be difficult to diagnose.

In Java, these scenarios correspond to specific exceptions: NoSuchMethodException for method lookups, NoSuchFieldException for field lookups, and WrongMethodTypeException for method handle invocations with incompatible types.

How to fix it

Ensure the MethodType specification matches the actual method signature exactly. Verify the return type, parameter count, parameter types, and their order.

Code examples

Noncompliant code example

public class UserService {
    public void updateUser(int userId, String name) {
        // Implementation
    }

    public static void main(String[] args) throws Exception {
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        // Wrong parameter types: String instead of int
        MethodHandle mh = lookup.findVirtual(
            UserService.class,
            "updateUser",
            MethodType.methodType(void.class, String.class, String.class) // Noncompliant
        );
    }
}

Compliant solution

public class UserService {
    public void updateUser(int userId, String name) {
        // Implementation
    }

    public static void main(String[] args) throws Exception {
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        // Correct parameter types: int and String
        MethodHandle mh = lookup.findVirtual(
            UserService.class,
            "updateUser",
            MethodType.methodType(void.class, int.class, String.class)
        );
    }
}
