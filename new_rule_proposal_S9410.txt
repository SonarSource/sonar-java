# Proposed Approach for S9410: MethodHandle and VarHandle lookups should use matching type signatures

## Summary

Implement S9410 as a semantic, conservative check for the JDK dynamic lookup APIs that accept a programmatically constructed method or field signature. The check should compare a statically recoverable `MethodType` or field type against the declarations in the referenced source type and report only mismatches that can be proven from source code. It should cover `MethodHandles.Lookup.findVirtual`, `findStatic`, `findSpecial`, and `findConstructor`, together with `findVarHandle` and `findStaticVarHandle`. Calls with non-constant class/name/type information should be ignored rather than guessed.

The checked-in RSPEC metadata is ready and identifies the rule as a Critical reliability bug rule with a constant five-minute remediation cost. No implementation source files should be changed as part of this proposal.

## Rule Behavior

Report a lookup when all of the following are statically known:

- The receiver is a `MethodHandles.Lookup` and the invoked method is one of the supported lookup methods, or the receiver is the `MethodHandles` utility for a supported `VarHandle` lookup.
- The referenced class is a class literal or another expression whose type/declaration can be resolved reliably.
- The member name, when applicable, is a compile-time string constant.
- The requested method return type and parameter types, or requested field type, are represented by resolvable class literals/type expressions.
- No method or field with the requested signature and required static/instance form exists in the resolved target hierarchy.

The rule should allow valid overloads, inherited members, constructors, static versus instance lookups that match the selected API, primitive types, reference types, arrays, and signatures assembled through simple local constants when the semantic model can resolve them. It should not attempt to emulate access-control behavior or flag a lookup merely because it may fail for an unrelated reason such as visibility, caller privileges, module boundaries, or runtime class-loader differences.

The diagnostic should identify the supplied `MethodType` for method lookups and the supplied field type for `VarHandle` lookups, with a concise message such as “Use a type signature matching the target method” or “Use the declared type of the target field.” If the target declaration cannot be resolved with certainty, do not report an issue.

## Proposed Approach

Use `IssuableSubscriptionVisitor` and subscribe to `METHOD_INVOCATION`. Match the supported JDK methods using `MethodMatchers`, which avoids depending on textual receiver names and prevents similarly named application methods from being treated as JDK lookups.

Separate the implementation into small extraction and comparison operations:

- Extract a constant `Class<?>` argument, a constant member name, and a `MethodType` description from the invocation tree.
- Normalize each class literal to the analyzer's resolved `Type`, preserving primitive/reference distinction and array dimensions.
- Resolve the target type's methods, constructors, or fields through the semantic model, including inherited members where the selected lookup API searches them.
- Compare arity, parameter order, parameter types, return type, and static/instance form as applicable.
- Report only a proven mismatch; return without reporting for variables, method calls, conditional expressions, reflection, unresolved symbols, or unsupported `MethodType` factories.

The first implementation should remain source-based and local to the check. It should not add an abstract base class or alter build files. A quick fix is not recommended initially because choosing a correct replacement type can be ambiguous when overloads or fields are involved.

For `MethodType.methodType`, support the overloads whose arguments can be completely recovered from syntax and semantics: a return `Class` plus zero or more class arguments, and array/list forms only when their contents are compile-time recoverable. Treat `MethodType` variables as analyzable only if constant propagation already exposes their initializer through existing analyzer utilities; otherwise skip them. For `VarHandle`, compare the requested field type with the resolved declaration and distinguish `findVarHandle` from `findStaticVarHandle`.

## Algorithm

1. Visit each method invocation and match the declaring type and method name against the supported `MethodHandles.Lookup` and `MethodHandles` APIs.
2. Select the target class, member name, requested signature, and lookup kind from the matched API's argument positions.
3. Resolve the target class expression. Accept class literals and other expressions with an unambiguous resolved type; stop when the class cannot be determined.
4. For method lookups, require a compile-time member name and decode the `MethodType` argument into an ordered return type and parameter-type list. Preserve primitive types exactly; do not apply boxing equivalence.
5. For field lookups, require a compile-time member name and decode the requested field `Class` argument.
6. Search the target declaration and the relevant supertype/interface hierarchy for a method, constructor, or field matching the lookup operation. Respect the operation's static/instance distinction and use the API's normal member-search semantics.
7. Compare the requested method return type and every parameter type with the declaration. For constructors, validate the constructor parameter list and the required constructor `MethodType` return convention. For fields, compare the declared field type exactly.
8. If an exact compatible declaration exists, emit nothing. If no exact declaration exists but the target/member/signature information was fully resolved, report the signature expression at the `MethodType` or field-type argument.
9. If overload resolution, inheritance, generic substitution, source availability, constant evaluation, or API semantics are ambiguous, emit nothing. Add focused tests for every deliberate bailout so future changes do not turn uncertainty into false positives.

- `org.sonar.java.checks.verifier.CheckVerifier`: verify expected issue locations and messages in both semantic and no-semantic test modes.
- Existing constant-value utilities in `java-checks` should be preferred for string and simple variable evaluation; do not introduce a bespoke constant-propagation engine for this rule.

Before implementation, confirm the exact available semantic APIs for enumerating members and supertypes in the current branch. If the API cannot reliably model the full lookup hierarchy, constrain the first version to directly resolved source declarations and document the resulting accepted false negatives rather than approximating with names alone.

## Test Strategy

Add a standard `S9410CheckTest` using `CheckVerifier` and a shared sample file. Run the sample once with semantic analysis and once with `.withoutSemantic()` as required by repository conventions. The no-semantic suite should verify that unsupported or unresolved cases are safely ignored; if the rule can perform a purely syntactic check for a case, explicitly test that behavior.

The sample should use small local classes and JDK types, avoiding external dependencies. Include exact-message assertions for representative issues, and place markers on the `MethodType` or field-type expression rather than the entire invocation. Test both direct literals and simple constants, overloads, primitive/wrapper differences, parameter order, arity, return types, arrays, inheritance, constructors, static/instance lookup variants, and VarHandle field access. Add cases with unresolved names and dynamic values to lock in the conservative behavior.

Do not add ruling expectations locally. Ruling files are generated and updated by the CI workflow described in the repository guidance.

## Expected Cases Covered

### Noncompliant patterns

- The RSPEC generated example: `findVirtual(UserService.class, "updateUser", MethodType.methodType(void.class, String.class, String.class))` when `updateUser` actually takes `(int, String)`; the parameter type is wrong.
- A method lookup whose `MethodType` has the right parameters but the wrong return type.
- A method lookup omitting a parameter, adding one, or placing valid parameter types in the wrong order.
- A primitive/reference mismatch such as requesting `Integer.class` for a method declared with `int`, or requesting `int.class` for a method declared with `Integer`.
- A `findStatic` request for an instance method, or a `findVirtual` request for a static-only target, when the declaration is otherwise known.
- `findConstructor` with a parameter list that does not match any constructor of the target class.
- `findVarHandle` or `findStaticVarHandle` with a requested field type different from the declared field type, including primitive versus wrapper mismatches.
- A lookup for a known member name with a fully constant signature for which no matching overload exists.

### Compliant patterns

- The RSPEC compliant example using `void.class, int.class, String.class` for `updateUser(int, String)`.
- Exact matches for zero-argument, multi-argument, overloaded, primitive, reference, array, and `void`-returning methods.
- Valid inherited method lookups when the selected lookup API can search the superclass or interface hierarchy.
- Valid constructor signatures and valid static versus instance lookups.
- VarHandle lookups using the exact declared field type for both instance and static fields.
- Signatures built from supported compile-time constants when their values are unambiguous.
- Dynamic member names, target classes, or `MethodType` values that cannot be proven correct or incorrect; these are compliant from this rule's reporting perspective and should not be flagged.
- Methods or fields that are unavailable in source, unresolved, or affected by access/module rules unrelated to the requested type signature; leave those to the runtime/API checks and avoid duplicate diagnostics.

## Expected Accepted FN/FP

### Accepted False Negatives

- Signatures assembled through arbitrary runtime logic, reflection, configuration, or data loaded from outside the compilation unit; the analyzer cannot prove their values safely.
- Targets supplied through aliases, factory methods, class loaders, or generic abstractions that do not resolve to one concrete declaration.
- Bytecode-only, generated, or separately compiled target members unavailable to the semantic model.
- Complex `MethodType` construction through unsupported overloads or mutable collections, unless existing constant evaluation can establish every element.
- Subtle runtime lookup behavior involving erased generic signatures, bridge methods, hidden classes, nestmates, modules, caller sensitivity, or class-loader identity when source-level type comparison cannot model it exactly.

### Accepted False Positives

- The preferred design should have no intentional false positives for fully resolved signatures. A conservative bailout is preferable to a warning in uncertain cases.
- A possible residual false positive may occur where the Java semantic model resolves a declaration but cannot represent a runtime class-loader or generated-member distinction. This should be documented and covered by a regression test if discovered in ruling or integration testing.
- Access-control or visibility failures should not be treated as S9410 false positives: if reported by another rule or at runtime, they are outside this rule's type-signature contract. The implementation must avoid reporting those cases solely because a type match was not found when the search was incomplete.
