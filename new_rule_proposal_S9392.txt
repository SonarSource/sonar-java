# Proposed Approach for S9392: Redundant range checks should be removed

## Summary

Implement a new rule that detects redundant range checks on the same variable within a single boolean AND expression. When multiple range comparisons (>, <, >=, <=) reference the same variable, one comparison may be logically implied by another. For example, `x >= 0 && x >= 5` contains a redundant check because `x >= 5` already implies `x >= 0`. The rule should identify and report the redundant condition, suggesting removal of the weaker check.

## File Locations

- Rule class: `java-checks/src/main/java/org/sonar/java/checks/RedundantRangeCheckCheck.java`
- Test class: `java-checks/src/test/java/org/sonar/java/checks/RedundantRangeCheckCheckTest.java`
- Test sample: `java-checks-test-sources/default/src/main/java/checks/RedundantRangeCheckCheckSample.java`

## Rule Behavior

The rule detects when a conditional expression contains multiple range checks on the same variable where one check is redundant because it is implied by another check in the same AND expression.

**What the rule should detect:**
- Multiple range comparisons (`<`, `<=`, `>`, `>=`) on the same variable connected by `&&`
- Cases where one range check implies another (the redundant one)
- Both `x >= 0 && x >= 5` (redundant: `x >= 0`) and `x >= 5 && x >= 0` (redundant: `x >= 0`)

**What the rule should NOT detect:**
- Comparisons on different variables (e.g., `x >= 0 && y >= 0`)
- Single range checks
- Comparisons connected by `||` (OR) - these are not redundant even if they reference the same variable
- Equality comparisons (`==`, `!=`) - these are not range checks
- Nested AND expressions (e.g., `(x >= 0 && x >= 5) || y > 0`) - only flat AND chains are analyzed

## Proposed Approach

Use `IssuableSubscriptionVisitor` to listen for `Tree.Kind.AND` nodes. When an AND expression is found, extract all range comparison operands (flattening nested ANDs), group them by the variable being compared, and check for redundant implications within each group.

This approach is preferred over listening to individual comparison operators because:
1. We need to analyze the conjunction as a whole to detect redundancy
2. The AND structure provides natural grouping for the analysis
3. It mirrors the pattern used in `DuplicateConditionIfElseIfCheck` for analyzing compound conditions

## Algorithm

1. **Register for AND nodes**: Implement `nodesToVisit()` to return `Tree.Kind.AND`.

2. **Collect range comparisons**: When `visitNode` receives an AND tree:
   - Flatten nested AND expressions by recursively collecting operands
   - For each operand, check if it is a range comparison (`<`, `<=`, `>`, `>=`)
   - Skip equality operators (`==`, `!=`) and non-comparison expressions

3. **Extract comparison metadata**: For each range comparison:
   - Use `ExpressionUtils.skipParentheses()` to unwrap parentheses
   - Identify the variable being compared (left or right operand, whichever is an identifier)
   - Determine the comparison operator and constant value
   - Normalize to a canonical form: variable on left, operator, constant

4. **Group by variable**: Use a `Map<IdentifierTree, List<NormalizedComparison>>` to group comparisons by the variable being compared.

5. **Detect redundancy**: For each variable's comparison list:
   - For each pair of comparisons (a, b):
     - If `a` implies `b`, then `b` is redundant
     - Comparison A implies comparison B when:
       - Both are `>=` comparisons with A's constant >= B's constant
       - Both are `<=` comparisons with A's constant <= B's constant
       - Both are `>` comparisons with A's constant >= B's constant
       - Both are `<` comparisons with A's constant <= B's constant
       - A `>` comparison implies a `>=` comparison with a lesser or equal constant
       - A `>=` comparison implies a `>` comparison with a greater constant
   - Report the redundant comparison with a message: "Remove this redundant range check; it is implied by the '{implied_by}' check."
   - Add a secondary location pointing to the implying comparison

6. **Handle edge cases**:
   - Skip comparisons where the constant cannot be resolved (e.g., variable on right side)
   - Skip if either operand of the comparison is not a constant
   - Skip if the variable cannot be identified (e.g., complex expression)

## Recommended Helpers

- **`ExpressionUtils.skipParentheses(Tree)`** - Used to unwrap parentheses from operands
- **`ExpressionUtils.areVariablesSame(ExpressionTree, ExpressionTree)`** - Used to verify both sides of comparisons refer to the same variable
- **`LiteralUtils.intLiteralValue(Tree)`** / **`LiteralUtils.longLiteralValue(Tree)`** - Used to extract constant values from literals

No new helper classes are required. The rule can be implemented entirely within the check class using existing utilities.

## Test Strategy

The test file should cover the following patterns:

### Compliant patterns (no issues expected)
- Single range check: `if (x >= 0)`
- Different variables: `if (x >= 0 && y >= 5)`
- OR operator: `if (x >= 0 || x >= 5)`
- Equality comparisons: `if (x == 0 && x == 5)`
- Mixed operators that don't create redundancy: `if (x >= 0 && x <= 10)`
- Parenthesized expressions: `if ((x >= 0) && (x >= 5))` - should still detect

### Noncompliant patterns (issues expected)
- Same operator, different constants: `if (x >= 0 && x >= 5)` - redundant `x >= 0`
- Reversed order: `if (x >= 5 && x >= 0)` - redundant `x >= 0`
- Strict vs non-strict: `if (x > 0 && x >= 0)` - redundant `x >= 0`
- Less-than comparisons: `if (x <= 10 && x <= 5)` - redundant `x <= 5`
- Greater-than comparisons: `if (x > 5 || x > 0)` - redundant `x > 0`
- Multiple redundancies: `if (x >= 0 && x >= 5 && x >= 10)` - redundant `x >= 0` and `x >= 5`
- Nested AND: `if ((x >= 0 && x >= 5) && x >= 10)` - should handle nested ANDs

## Expected Accepted FN/FP

### Accepted False Negatives
- Range checks where the constant is a variable or complex expression (e.g., `x >= min && x >= max`)
- Range checks across different scopes (e.g., in different branches of an if-else)
- Range checks on method return values (e.g., `getVal() >= 0 && getVal() >= 5`)

### Accepted False Positives
- None anticipated. The rule only flags cases where one comparison is logically implied by another, which is always a code smell.
